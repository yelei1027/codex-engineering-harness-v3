01 / START

第一次使用，集中完成接入

本文对应 v3.2.0；正式发布不代表所有原生验收已通过。请同时阅读 RELEASE-3.2.0.md 中的验证范围与已知限制；历史报告只证明它记录的版本。
  1. 准备 Harness 本体。按 README 核对 Linux x86_64、Git、Node/npm、Python、uv、Docker Compose、用户级 systemd、Codex Desktop 与私有仓库访问。新版源码的完整准备入口是 bin/harness install --prepare；额外 Provider Key 在用到时配置。harness preflight 被当前权限拒绝的检查显示 UNVERIFIED（未核验），不代表组件缺失；在已授权且可访问组件的环境重跑，不要据此安装或重启服务。未核验仍阻止完整准备。
  2. 查看项目接入影响。在任意目录执行 harness prepare /你的项目路径。它先展示 Git、配置、技能、权限默认与 Hook 影响，保留原文件。
  3. 确认这份准备范围一次。已有适用授权就继续；否则确认后执行 harness prepare /你的项目路径 --apply。初始化本地 Git不创建提交或远端仓库。
  4. 集中完成原生步骤。在 Codex Desktop 以该项目为主文件夹打开新会话，按原生机制审阅项目配置与需要的 L2 Hook。配置写入不等于当前聊天已经加载，也不等于 Hook 已信任。若提示未注入规划，先用 harness check 检查安装文件；入口、规划脚本或锁定清单缺失或被改时，先准备完整版本，再核对信任与实际注入。
  5. 明确选择 Harness。在聊天中说“用 Harness”。以后本聊天沿用该选择；无需每轮重复 $、@，切换项目仍核对绑定与权限。
用 Harness，先帮我只读检查这个项目，
给出有依据的优化建议，再引导我确认范围。

普通聊天、未请求 Harness 的开发、附件里出现 Harness 或明确要求不用 Harness，都不激活这套流程。

03 / CONTROL

确认范围与实际权限都必须成立

范围批准

来自可信的人类消息或宿主原生批准事件。CLI 的 --apply、任务节点、计划、Hook 输出和“approved”文件只是数据，不能认证人类同意。

原生边界

项目准备提供 harness-inspect（需求检查：只读）。在消息框下的原生权限菜单选择它，再核验下一轮实际 read-only。桌面保存的选择可覆盖配置默认；设置页只读不证明聊天已切换。

具体范围批准后，可由原生“请求批准”模式开放工作区写权限，范围内自主实现；完成或取消后恢复 harness-inspect 并重新核验。该流程仍需原生操作，安装不会替你选择权限或信任 Hook。菜单缺项时记录实际缺口。

App/MCP 副作用不自动继承 Shell 沙盒保护。新登记工具使用原生 prompt；既有同名配置与逐工具覆盖须单独核验。权限未知时，先完成明确的原生步骤，停止受保护写入。

同一批准范围内的源码修复和重新验证不会自动使范围批准失效。旧测试与审查可能因内容变化失效，需要重新验证，权限批准与技术证据应分别核对。

一个 Main Router，按需组合能力

层负责什么什么时候用
harness-entry发现已安装入口、核对接入，转交项目 Main。人类明确选择 Harness；不创建第二套工程编排。
harness-dev / Main Router控制目标、范围、风险、调用与交付。已选择 Harness 的项目任务。
方法 Skills澄清、设计、TDD、诊断、审查等方法。风险与未知量需要时；implement/implement-spec 仅显式进入上游编排。
context-mode / CodeGraph / MarkItDown上下文、真实代码结构和文件转换。按需要调用；stdio 组件由受管用户进程组管理。
PowerContext Basic显式 Handoff、指定 Scope/Revision 的跨会话读取。真实交接需要时；Full 自动记忆另需 Provider 与验证。
截图能力默认使用当前 Codex 的图像理解；本地截图渲染与第三方生成分别检查。视觉任务；第三方生成 Key 未配置时据实说明。
真实独立审查按风险提供第二视角与可核对结果。高风险或有独立性价值的工作；Main 换口吻不算子 Agent。
可信 Hook / 持久计划生命周期事件、选定计划及上下文恢复。长任务或已选 L2 接入；Hook 不承担业务主编排。

接入配置与任务风险是两回事

默认接入配置 L2 表示准备项目生命周期 Hook；每个任务仍按失败后果与未知量判断 L0/L1/L2 风险。低风险任务不因接入 L2 而机械跑全部 Skills 或子 Agent。高风险小改动仍需适用独立审查。

06 / CONTINUE

中断后核对事实，再接着完成

  • 安装失败：保持同一版本与目录，按日志修复失败步骤后重试。部分服务启动失败时，核对构建、端口与挂载后复用并续启，保留数据；构建变化或未知消费者会阻止重试，按提示准备隔离候选。未受管非空目录不会被删除。
  • 卸载中断：用 harness uninstall-recover 操作ID 预览，再按适用授权 --apply。恢复所有根与配置前先检查完整集合，出现冲突就保留当前文件和备份。停止的服务另行重建/启动。
  • 重装数据：harness recover-data 预览，--apply 恢复。持久记录已移动与未移动项目；重试先核对完整集合，不覆盖后来数据。源码缓存只备份、不恢复执行。
  • 跨版本记忆：harness recover-memory 预览并按授权恢复原数据卷；完整准备入口自动接续。保留原地址、Scope 和 Revision。镜像不同、未知消费者、端口占用或恢复代次变化时保留冲突，不自动升级数据库。启动与精确记忆回读分别验证。
  • 上下文压缩：恢复 Hook 使用项目准备时绑定的安装状态目录，不借用另一安装的记录；更新定义后按原生提示重新核对信任。保留已绑定任务实例、选定 plan-id、当前代码、范围和证据。忽略目录的证据与分支变化仍检查；同名任务重建不继承旧摘要。
  • 正式交接：确实需要跨会话时保存 Handoff；普通压缩只保存本地 Checkpoint，不强制额外交接或远端同步。

文件恢复、依赖重建、数据恢复和服务重启各有可观察结果。单个退出码、容器 running 或 AI 自报完成不能替代对应业务验证。

07 / EVIDENCE

可用、待配置、待信任、未验证分别记录

技术证据

当前源码回归、真实组件调用、原生权限探针、服务与数据生命周期，以及实际独立审查各自注明范围。源码发生变化后，受影响证据需要更新。

发布证据

最终不可变快照、适用真实桌面主流程、包干净安装、风险审查和远端版本回读全部对应同一版本。当前实施与专项通过不代表完整 PRD 或正式发布已完成。

发行包排除机器绑定、凭据、会话、业务数据和规划记录；原始运行报告不随包分发。摘要只保留固定状态，缺少当前源码绑定时标为未验证。

权威来源：README · 安装说明 · 权限说明 · 工程节点契约 · PRD #1。
